# PayPal conservative GSM policy

`config/gsm/paypal.json` is an explicitly imported policy asset, not an automatic database migration. Its six `rules` are individual existing `GsmCreateRequest` bodies. They conservatively select `do_default` for PayPal processor codes 9500 (`SUSPECTED_FRAUD`), 5180 (`INVALID_OR_RESTRICTED_CARD`) and 9520 (`LOST_OR_STOLEN`). PayPal says to use another card and not retry the same card: [sandbox card testing](https://developer.paypal.com/sandbox-testing/card-testing/). The deprecated decision/flags and current `feature=retry` / `feature_data.retry` agree. No rule grants automatic retry permission, step-up, clear-PAN or alternate-network retry.

The GSM key is **global** `(connector, flow, sub_flow, code, message)`. There is no merchant component. Do not apply this asset automatically to a shared or production database. The executable controls permit only a fresh, uniquely owned isolated PostgreSQL container bound to the actual HS process. They do not overwrite an unrelated existing rule, including an existing retry policy. Take an operator-reviewed exact snapshot before any import elsewhere.

The actual retry lookup uses connector `paypal`, flow `Payment`, and the Rust authorize flow name `Authorize` as subflow. It tries issuer lookup first: for Visa and processor code 9500, both `code` and `message` are `Network:Visa|IssuerCode:9500`. Only if that lookup misses does it use the actual connector processor code and full mapped message, including punctuation. The asset contains one issuer-first and one connector fallback record for each code. Its distinct `unified_code` labels identify those records; they are diagnostic labels, not standardized gateway codes. Other networks are not claimed covered. `Authorize` as the top-level flow, another subflow, or a different message is a different key.

All four existing admin API operations use POST with `api-key` authentication: `/gsm`, `/gsm/get`, `/gsm/update`, `/gsm/delete`. Resolve the admin key through an environment variable such as `HYPERSWITCH_ADMIN_API_KEY` in memory. Never include its value in command text, request logs, context JSON, receipts or commits. There is **no GSM listing endpoint**. Verify every affected exact key through `/gsm/get`; a delete acknowledgment alone is not evidence of cleanup.

Run the existing `scripts/paypal_ucs_regression_runner.py` with its standard `--require-committed`, exact HS/UCS build receipts, UCS repo/endpoint, context, journal and output arguments, selecting `--case gsm_hard_decline_9500` (or another committed GSM case). The original 52 cases remain; eight hand-authored GSM controls were appended to the existing HS fixture. No matrix generator owns that fixture and no UCS generated matrix is changed.

A GSM case's existing operator context supplies normal `bindings`, one standard payment `steps` entry (`body_env`, `path`, `reconcile_path`, `proof_path`) and `kind=production_fixture`. Its `gsm` context supplies:

- `admin_key_env`: environment variable name only.
- `wallet_mask_receipts`: current source-origin observation reports collectively proving both actual sinks for Apple PSP, Apple HS and Google HS modes, bound to the exact current source, binaries and HS PID, plus the precise Google PSP applicable exception below.
- `owned_database`: `fresh_isolated=true`, actual `container_id`, exact `container_name`, original `run_id`, `created_after` UTC timestamp and `database_name`. The consumer checks the container ID/name/date, loopback PostgreSQL port and the bound HS process's `ROUTER__MASTER_DATABASE__HOST`, `PORT`, and `DBNAME` environment values in memory. A runtime using a different configuration source must provide a separately reviewed binding; it cannot bypass this check.
- `engine_preflight_path`: a read-only path on the existing loopback `PAYPAL_HS_PROOF_BASE` producer. That producer must observe the actual HS retry configuration and selected routing: automatic retries enabled, positive remaining budget, and at least two eligible owned inert fixture MCAs. An authored expected-result file cannot satisfy this contract.

The real payment must use a new uniquely named local inert subject and the actual HS-to-UCS path. The engine producer must prove the actual matched five-part key (or an observed miss), `do_default`, one initial fixture call, zero alternate calls, zero external provider calls, unchanged positive initial budget, eligible MCA identities and exact running binary/PID bindings. Positive matches also require the selected issuer record's actual `unified_code` in failed payment/readback. CRUD readback or zero fallback calls alone never establishes engine coverage: retry exhaustion or a missing alternative would make that result meaningless. Missing producer instrumentation is `NOT_RUN`, not a manufactured pass. The unknown-code and wrong-flow/subflow/message controls first prove no valid issuer or connector rule already matches; otherwise they are `NOT_RUN`.

The consumer snapshots complete public GSM records atomically before mutation and journals every administrative write before sending it. After interruption, keyed GET distinguishes the known prior and desired record hashes; an ambiguous third state fails closed. Payment writes already recorded in the normal journal are reconciled by GET and never replayed. A `finally` cleanup restores exact preexisting records, or deletes newly created records, and verifies each affected key again. Restoring a nullable original field may require deleting the temporary record then recreating the exact snapshot; update-null semantics are not assumed to clear fields. Unexpected concurrent records are never deleted. Cleanup failures remain explicit and must be reconciled before further work.

Evidence states are separate: the asset/consumer are **IMPLEMENTED**; actual admin requests and checked wire shapes may become **GRADED**; real provider outcomes require an independent live oracle before **VERIFIED**. Local inert engine controls never count as PayPal live verification. Full positive smart retry remains **SPEC_GAP / NOT_RUN** until a documented positive retry permission and actual engine controls are established. Existing merchant/profile retry enablement and maximum retry configuration are separate operator choices and are not enabled by this seed.

Wallet log checks recognize only the locked masking library's exact `*** alloc::string::String ***` marker or literal `***` in actual `ApiLogs` at the selected wallet mode and exact request path. Actual `ConnectorApiLogs` accepts literal `***` only. Incorrect type names, spaces, partial markers, wrong wallet/path or unrelated masked credentials never count. Both sinks still need actual PID/descriptor/inode/offset binding, generated request UUID, payment subject, absence of the inert canary value and an observed masked entry. Previous failures remain historical evidence. This oracle fix does not change pre-order payment sync behavior or relax any payment readback assertion.
