## Execution mode

Omit `execution_kind` or send `"normal"` to keep the existing payout flow.
Send `"external_vault_proxy"` to select the external-vault proxy flow through this
same endpoint. The selector is supported only on create; update and confirm reject it.

<Note>
  Proxy execution is not available in this contract-only release. An authenticated
  proxy create request with `payout_id` returns HTTP `501 Not Implemented` before
  normal card retrieval, payout creation, or connector execution. Execution is delivered in
  the subsequent Hyperswitch core and UCS changes.
</Note>

### Proxy request contract

The merchant supplies a unique `payout_id`, a saved Hyperswitch `payout_method_id`,
and its owning customer, not a vault token. The payment method must already have
been vaulted through the payments flow. Hyperswitch will retrieve the token internally and
resolve vault configuration through the provider business profile.

Once proxy execution is implemented, omitted flags default to `confirm=true`,
`auto_fulfill=true`, `payout_type=card`, and `recurring=false`. Matching explicit
values are accepted; conflicting values, inline `payout_method_data`,
`payout_token`, `client_secret`, and payout-link options are rejected only for
proxy requests. There is no SDK flow or separate confirm call.

```bash
curl --request POST 'https://api.example.com/payouts/create' \
  --header "api-key: ${HYPERSWITCH_API_KEY}" \
  --header 'Content-Type: application/json' \
  --data-raw '{
    "execution_kind": "external_vault_proxy",
    "payout_id": "payout_proxy_merchant_1001",
    "merchant_order_reference_id": "merchant_payout_1001",
    "amount": 1000,
    "currency": "USD",
    "customer_id": "cus_external_vault_123",
    "payout_method_id": "pm_external_vault_123",
    "profile_id": "pro_external_vault_123",
    "confirm": true,
    "auto_fulfill": true,
    "payout_type": "card",
    "recurring": false,
    "entity_type": "Individual",
    "connector": ["cybersource"]
  }'
```

Successful proxy execution will reuse `PayoutCreateResponse`; the connector
determines the final payout status. No vault token or real card data is returned.

### Retry safety

`merchant_order_reference_id` is a reconciliation reference, not a deduplication
key. Current payout create does not acquire a request lock. Repeated creates
without the same `payout_id` can create separate payouts; a timeout must not be
treated as proof that no money moved. Use a stable merchant-supplied `payout_id`
for retries and retrieve that payout to inspect its status. An existing ID
returns the existing duplicate-payout error, not a replay of the create response.

Proxy requests must supply `payout_id`; omission returns HTTP `400`. Normal
requests may still omit it and receive an autogenerated ID. PR1 returns HTTP
`501` for proxy requests with an ID until proxy execution is implemented.

### Storage rollout

Apply the additive `payout_attempt.execution_kind` migration before deploying
code that queries or writes the column. The database default keeps old rows and
old-version inserts in `normal` mode. The new domain and Diesel cache models use
`serde(default)` to read old Redis records and queued inserts without this field;
no payout-cache flush is needed for that upgrade.

Stop and drain all applications and workers using the column before applying
the down migration, which removes both the column and enum. Once proxy payouts
exist, reconcile them before rolling back to code that cannot enforce their
execution marker. Do not use a cache flush to discard proxy-mode protection.
